## Context

`backend/internal/service/webpush.go` の `SendWebPush` メソッドは現在 `TTL: "86400"` を設定している。Push Service は最大 24 時間まで通知をキューイングするため、デバイスがオフラインの夜を越えて翌日（場合によっては翌々日）に配信されうる。

曜日計算ロジック（`formatDateLabel`・`weekdays` 配列・`toJSTDateStr`）はコード分析とテスト実行により正確であることを確認済み。スケジュールデータ（`schedule.json` と `schedule.ts`）にも不整合なし。「曜日が間違っている」症状の根本原因は TTL による遅延配信。

## Goals / Non-Goals

**Goals:**
- Web Push TTL を 28800 秒（8 時間）に短縮する
- 曜日計算の JST 日付境界テストを追加してリグレッションを防ぐ

**Non-Goals:**
- 通知の再送・リトライ機構の実装
- 通知スケジューリングの仕組みそのものの変更
- 多地区対応（現在は 1 地区固定）

## Decisions

### TTL を 86400 → 28800 秒に変更する

`backend/internal/service/webpush.go` の `req.Header.Set("TTL", "86400")` を `req.Header.Set("TTL", "28800")` に変更する。

**理由:** 28800 秒（8 時間）は以下の要件を満たす最大値：
- 夜 20 時の通知 → 翌朝 4 時以降に届いた場合は破棄（収集前日の夜の文脈で意味を持つ通知）
- 朝 7 時の通知 → 午後 3 時以降に届いた場合は破棄（当日朝の文脈を失っている）

**代替案:** TTL をさらに短く（例: 3600 秒 = 1 時間）にする案もあるが、都心部での FCM/APNs 配信遅延（数十分〜1 時間）を考慮すると短すぎて実用的でない。

### 曜日計算テストの追加

`backend/internal/service/` に既存の `webpush_test.go` に追記するか、新ファイル `notify_test.go` を作成し、以下を追加テストする：

1. `formatDateLabel` を複数の日付（月・水・土・日）で呼び出し、返り値が正しい曜日文字を含むことを確認
2. `toJSTDateStr` を JST 日付境界付近の UTC 時刻（UTC 14:59、UTC 15:00、UTC 15:01）で呼び出し、日付文字列が正しいことを確認
3. `runBatchNotify` のロジックを、JST 深夜 0 時をまたぐ UTC 時刻（`jstHour` = 23、0、1 の各パターン）でシミュレートするテーブルテスト

## Risks / Trade-offs

- **TTL 短縮によるカバレッジ低下**: デバイスが 8 時間を超えてオフラインだった場合、通知が届かない。これは意図した動作であり、「古い通知が届かない」ことよりも「間違った曜日の通知が届く」ほうが混乱を招くため許容する。
- **Apple APNs との互換性**: APNs は TTL ≥ 0 を受け入れる。28800 秒は問題なし。
